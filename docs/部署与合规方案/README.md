# 春之声 · 俄罗斯部署与 152-FZ 合规方案

> 版本：v1.1 · 日期：2026-09-14 · 状态：待评审

---

## 1. 背景与目标

春之声品牌独立站面向俄罗斯 C 端用户（留资 → 渠道商建联 → 落地中国接待），
网站（含 C 端 + B 端订单后台）需处理**俄罗斯公民个人数据**，必须满足俄罗斯联邦
《个人数据法》（**152-FZ**）的本地化要求。

**关键业务约束**：

1. **数据需传回国内**：订单/留资数据最终要同步到中国总部，供超管与内部处理
2. **俄境内只有合作渠道服务商**：春之声在俄罗斯无自营法人主体，境内只有合作的
   渠道商（俄罗斯旅行社等）

这两条决定了本方案的核心难点不在技术，而在**"谁在俄境内承担合规运营者角色"**。

本方案目标：

- 明确 152-FZ 合规硬约束
- 厘清"运营者主体"这一核心判断
- 给出整体部署架构与数据流向（含跨境回传）
- 对比俄罗斯境内云服务提供商
- 给出分阶段落地路径与风险提示

## 2. 合规硬约束：152-FZ

| 条款 | 要求 |
| ---- | ---- |
| 第 18 条第 5 款（2015 年 9 月起强制） | 处理俄公民个人数据时，**收集、系统化、累积、存储、更新、提取** 必须使用**位于俄罗斯联邦境内**的数据库 |
| 跨境传输（2021 年修订） | 将个人数据传出俄境前，需**告知 Roskomnadzor**，且目的国需满足充分保护条件 |
| 用户同意（Consent） | 需以**俄语**向用户明示数据处理目的，并取得同意 |
| 隐私政策 | 需有俄语版隐私政策，说明运营者、处理目的、存储位置、用户权利 |

**核心结论**：

- 阿里云法兰克福节点、腾讯云、AWS 等**境外节点均不满足**存储本地化要求
- 面向 C 端收集用户信息的那一环，**必须**落在俄境内，不可用境外节点替代

## 3. 核心判断：谁才是"运营者"

152-FZ 的本地化义务落在**运营者**（实际收集、处理俄公民个人数据的主体）身上。
**留资数据的第一落地点**决定运营者是谁，进而决定责任与部署方案：

| 数据第一落地点 | 运营者 | 本地化义务 | 春之声角色 | 可行性 |
| -------------- | ------ | ---------- | ---------- | ------ |
| 春之声 C 端直接收集，数据进春之声系统 | 春之声 | 春之声须在俄境内存储 | 运营者 | 难（无俄主体） |
| 数据先落**俄罗斯渠道商**系统，再由渠道商回传 | 渠道商 | 渠道商（俄境内主体）承担 | 跨境接收方 | **顺**（契合现有业务） |

**结论**：你的业务流程天然是后者——"用户留信息 → 俄罗斯旅行社获取信息、与用户
建联 → 再与春之声对接"。因此最顺的合规架构是让**渠道商成为俄境内第一落地运营者**，
春之声作为跨境数据接收方。

## 4. 架构方案

### 4.1 双域架构（含跨境回传）

```
┌─────────────────────────────┐        跨境传输         ┌──────────────────────────┐
│  俄罗斯境内（合规域）          │  ┌──────────────────┐  │  中国（业务域）           │
│                              │  │ 标准合同条款       │  │                          │
│  C 端静态站（渠道商分发）       │  │ 告知 Roskomnadzor │  │  国内数据库（副本）         │
│        │ 留资表单             │──▶│ (152-FZ 第12条)   │──▶│  B 端：超管/总部           │
│        ▼                     │  └──────────────────┘  │  订单流转、报表、统计        │
│  渠道商系统（第一落地，运营者） │                         │                          │
│  俄境内数据库（主存储）        │                         │  （春之声内部处理）         │
│  B 端：渠道商查看自己订单      │                         │                          │
└─────────────────────────────┘                         └──────────────────────────┘
```

### 4.2 数据流向

1. 俄罗斯用户访问 C 端（俄境内，经渠道商分发）
2. 用户提交留资 → 数据**首次落入俄境内**（渠道商侧 / 俄境内库，满足 152-FZ）
3. 渠道商登录 B 端，仅查看自己渠道订单
4. 数据经跨境链路**回传国内**（副本），供超管与总部处理
5. 超管查看全部渠道订单、流转状态、筛选

### 4.3 三种落地路径

| 路径 | 做法 | 优点 | 风险/代价 |
| ---- | ---- | ---- | --------- |
| **A. 渠道商作为运营者** | 留资先落渠道商侧（俄境内、渠道商主体），再由渠道商回传国内 | 主体、支付、合规全由渠道商解决，最顺、最便宜 | 数据控制权让渡给渠道商，需合同强约束 |
| **B. 第三方 152-FZ 合规托管** | 找专门做"数据本地化托管"的服务商，租俄境内节点 + 合规主体 | 春之声保留数据控制权 | 要找靠谱服务商、额外付费 |
| **C. 春之声注册俄轻量主体** | 注册俄罗斯法人自建 | 合规最彻底、完全可控 | 成本高、周期长，MVP 不现实 |

> **MVP 建议**：走路径 A（渠道商作为运营者），合同锁定"数据归属归春之声、
> 渠道商有义务按约回传"；业务量起来、要彻底掌控数据时，再评估路径 B 或 C。

### 4.4 组件清单（路径 A 形态）

| 组件 | 建议选型 | 部署位置 |
| ---- | -------- | -------- |
| C 端静态站 | 现有 HTML/CSS/JS | 俄境内对象存储 / Nginx（渠道商侧） |
| 留资收集 | 渠道商系统 或 共用的俄境内 API | 俄境内 |
| 俄境内数据库 | PostgreSQL（主存储，合规） | 俄境内（硬约束） |
| 跨境同步 | API / 队列定时同步（脱敏最小化） | 俄 → 中 |
| 国内数据库 | PostgreSQL（副本） | 国内 |
| B 端后台 | 前端 SPA + 两域 API 网关 | 国内（超管）+ 俄境内视图（渠道商） |

## 5. 云服务提供商对比

### 5.1 俄罗斯本土云（IaaS/PaaS，生产首选）

| 服务商 | 定位 | 核心能力 | 适用场景 | 备注 |
| ------ | ---- | -------- | -------- | ---- |
| **Yandex Cloud** | 俄最大云厂商，对标 AWS | Compute VM、S3 兼容对象存储、托管 PostgreSQL/MySQL、LB、CDN、K8s | 正式生产、需弹性伸缩与托管数据库 | 生态最全，文档好，俄语原生 |
| **VK Cloud**（原 Mail.ru） | 第二梯队 | 类似 Yandex Cloud | 生产备选 | 与 VK 生态集成 |
| **Cloud.ru**（原 SberCloud） | 联邦储蓄银行旗下 | IaaS/PaaS 全栈 | 对合规/安全要求极高（金融、政府） | 银行背景，合规背书强 |
| **Selectel** | 老牌 IaaS 主机商 | VM、裸金属、S3、网络 | 生产 IaaS，性价比高 | 稳定成熟，圣彼得堡起家 |

### 5.2 俄罗斯轻量主机 / VPS（初期 MVP 快速落地）

| 服务商 | 定位 | 特点 | 适用场景 |
| ------ | ---- | ---- | -------- |
| **Timeweb** | 老牌主机商 | 便宜、俄语、管理面板友好 | 小站 / 验证期 |
| **Reg.ru** | 域名 + 主机一体 | 域名注册、主机、SSL | 域名托管一站式 |
| **Beget** | 主机商 | 性价比高，共享主机 + VPS | 轻量站点 |
| **RUVDS** | 专业 VPS | 纯 VPS，灵活 | 需要独立 IP/环境 |

### 5.3 明确排除

| 服务商 | 排除原因 |
| ------ | -------- |
| 阿里云 | 无俄境内节点，法兰克福等欧洲节点不满足 152-FZ |
| 腾讯云 / 华为云 | 无俄境内节点 |
| AWS / Azure / GCP | 2022 年制裁后退出俄罗斯，无法新购 |

## 6. 推荐部署方案（分阶段）

### 阶段一：MVP 验证期（成本优先 + 路径 A）

- **主体**：由合作渠道商承担运营者，用其主体注册云服务
- **选型**：Selectel（或 Timeweb）VPS 一台
- **部署**：VPS 上 Docker Compose 跑 API + PostgreSQL + Nginx（C 端静态站）
- **跨境回传**：定时任务 / API 把订单副本同步回国内
- **适用**：验证渠道分发模式、订单量小、快速低成本
- **风险**：数据控制权在渠道商，须先签数据归属与回传协议

### 阶段二：稳定增长期（弹性 + 托管优先）

- **选型**：**Yandex Cloud**（推荐主选，VK Cloud 备选）
- **部署**：
  - C 端静态站 → Object Storage + CDN
  - API → Compute VM / Managed Kubernetes
  - 俄境内数据库 → **Managed PostgreSQL**（托管，自动备份/高可用）
  - 国内副本 → 国内云（阿里云等）同步库
- **适用**：订单量上升、需要高可用与自动备份
- **跨境链路**：专用同步服务 + 传输加密 + 脱敏最小化

### 阶段三（可选）：彻底掌控数据

- **路径 B**：第三方 152-FZ 合规托管（保留控制权）
- **路径 C**：注册俄主体自建（合规最彻底）
- **选型**：Cloud.ru（原 SberCloud，银行背景，强合规）

## 7. 制裁与支付风险

| 风险 | 说明 | 应对 |
| ---- | ---- | ---- |
| 银行卡支付受限 | Visa/Mastercard 已退出俄罗斯，境外卡无法直接向俄服务商付款 | 需俄当地主体 + **MIR 卡**或当地银行账户；或渠道商代付 |
| 注册主体 | 俄云通常要求俄当地法人/税务信息 | 路径 A 下由渠道商主体注册，最省事 |
| 汇率与结算 | 卢布结算、跨境汇款受限 | 预算预留汇率与手续费 |
| 制裁合规审查 | 中俄主体间数据/资金往来需自查出口管制 | 咨询法务，避免触碰制裁红线 |

> **重要**：以上为通用风险提示，执行前建议结合公司主体情况，咨询熟悉中俄业务的
> 法务/合规顾问。

## 8. 跨境数据传输（数据回国内，刚需）

数据需传回国内，跨境传输成为**核心链路**，需重点处理：

1. **法律依据**：中国不在俄"充分保护"白名单内，需提供**充分保护措施**（标准合同
   条款 SCC），并**告知 Roskomnadzor**
2. **传输最小化**：跨境只传业务必需字段，能脱敏则脱敏
3. **技术保障**：传输加密（TLS）、访问控制、日志审计
4. **架构**：俄境内保留**主存储**（满足 152-FZ），国内保留**副本**（业务处理）
5. **同步机制**：API 实时推送或定时批量同步，带重试与幂等

## 10. 结论

- **存储必须俄罗斯境内**：法兰克福等境外节点一律不可用
- **运营者主体是核心**：俄境内只有渠道商 → MVP 走**路径 A（渠道商作为运营者）**，
  用合同锁定数据归属与回传
- **跨境回传是刚需**：俄境内主存储 + 国内副本，走 SCC + 告知 Roskomnadzor
- **云选型**：首选 Yandex Cloud，MVP 阶段用 Selectel / Timeweb VPS；彻底掌控数据时
  再评估路径 C（注册俄主体 + Cloud.ru）
- **最大障碍仍是主体与支付**，需优先与渠道商沟通并解决当地支付渠道
